# Как сдать выполненное задание

Работайте в собственном Fork и ветке solution/booking, созданных по [SETUP](SETUP.md#получение-своей-копии). Исходный репозиторий содержит заготовку задания; студенческие решения проверяют отдельно.

## Сохранить код и результаты

1. Выполните итоговый base, для уровня Э также expert. Отдельный smoke можно запустить для диагностики; итоговый base уже включает S01–S05. Команды и ожидаемые результаты находятся в [задании](ASSIGNMENT.md#этап-5-проверка-и-сдача-15-часа-и-общий-резерв).
2. Создайте в редакторе папку submission-results в корне проекта. Скопируйте в неё исходные starter-base-results.json/.md и итоговые base-results.json/.md из reports. Для Э добавьте expert-results.json/.md. Папка reports исключена из Git, а submission-results будет храниться в сдаваемой ветке. Не используйте git add -f для всего reports.
3. Проверьте git diff: в нём должны быть ваши изменения A/B/C и, если выполнялись, дополнения. В db/migrations должен лежать SQL-файл; исходные тесты, tests/cases.json и снимок tests/fixtures/starter_schema.sql должны оставаться без изменений.
4. Сохраните реализацию в Git:

```sh
git add app db/migrations
git diff --cached --stat
git commit -m "Fix concurrent booking"
git rev-parse HEAD
```

Если добавили собственный тест, до commit выполните также git add tests/student. Если осознанно меняли другие допустимые файлы, добавьте их по имени. При первом commit Git может попросить имя и email. Замените значения в кавычках своими, выполните команды ниже и повторите commit:

```sh
git config user.name "Имя Фамилия"
git config user.email "you@example.com"
```

5. Запишите полученный commit в поле «Commit реализации» в REPORT. Код и SQL для него должны совпадать с теми, на которых получены итоговые результаты. После изменения реализации повторите затронутые проверки и обновите commit. Последующий commit с отчётом и файлами результатов может иметь другой хеш.
6. Заполните остальные разделы REPORT и добавьте ссылку на видео. В таблице результатов укажите файлы из submission-results. Для невыполненного дополнения достаточно написать «не выполнялось».
7. Сохраните комплект и отправьте ветку:

```sh
git add REPORT.md submission-results
git diff --cached --stat
git commit -m "Add booking assignment report and results"
git push -u origin solution/booking
git rev-parse HEAD
```

Последний хеш обозначает весь комплект сдачи; укажите его вместе со ссылкой на ветку. Если дооформляете отчёт позднее, сделайте новый commit и push и сообщите обновлённый хеш. Не добавляйте .env, пароли, volumes и локальные эталонные решения из .instructor.

## Сценарий видео

| Время | Показать и объяснить |
|---|---|
| 0:00–0:45 | Что бронируется, версия starter, исходный красный сценарий с двумя победителями |
| 0:45–1:45 | Исправленный захват и подтверждение, состояние Redis и PostgreSQL |
| 1:45–2:45 | Истёкший/неверный holdId, один действительный владелец |
| 2:45–4:15 | Код ключевых изменений, SQL-ограничение, авторизация и commit |
| 4:15–5:15 | Итоговый base, известная гонка TTL, при выполнении дополнений их результат |

Допустимо сократить паузы запуска. Не нужно показывать установку Docker или записывать часы разработки. Для исходной ошибки используйте сохранённый результат B02 и поясните порядок действий по коду исходного commit. Если показываете живой запуск прежней версии, используйте отдельную копию по инструкции ниже. Не подменяйте наблюдения вымышленным выводом.

Для Э в пределах 3–6 минут выделите время на оба дополнения: E01 и защиту нового владельца от удаления, E02 и момент истечения TTL между авторизацией и commit. Объясните в видео то же усиление модели, которое предложено в REPORT.

Загрузите запись в хранилище с доступом по ссылке. Проверьте звук и откройте ссылку в приватном окне браузера или под другим аккаунтом. Проверяющий должен смотреть видео без запроса доступа. Вставьте ссылку в поле REPORT и проверьте её ещё раз после загрузки.

## Комплект сдачи

- Ссылка на репозиторий/PR и точный commit.
- REPORT с реальными результатами, анализом, временем и ссылкой на видео.
- Папка submission-results с JSON и Markdown исходного и итогового base.
- Для Э: expert-результаты и раздел об обоих дополнениях.

## Перед сдачей

1. На основном стенде получите бронь последовательным примером на свободном ресурсе и скопируйте bookingId. Выполните docker compose restart app, дождитесь healthy в docker compose ps. В /docs откройте GET /bookings/{booking_id}, подставьте сохранённый UUID и нажмите Execute. Должны вернуться 200 и прежние поля брони. Результат добавьте в REPORT.
2. Проверьте именно отправленные файлы в отдельной папке. В адресе замените YOUR_GITHUB_LOGIN своим логином:

```sh
git clone --branch solution/booking https://github.com/YOUR_GITHUB_LOGIN/concurrent-booking-lab.git concurrent-booking-review
cd concurrent-booking-review
git rev-parse HEAD
```

Сверьте хеш с комплектом сдачи. В редакторе создайте .env с одной строкой API_PORT=18080, чтобы не занять порт первого стенда. Если порт уже используется, выберите другой свободный.

```sh
docker compose -p booking-review up --build -d
docker compose -p booking-review ps
docker compose -p booking-review --profile test run --build --rm tests python tests/run_tests.py --mode base
```

Для проверки этой копии используйте http://127.0.0.1:18080/docs и добавляйте -p booking-review во все команды Compose. Так у неё будут отдельные контейнеры и PostgreSQL volume. При выполненных дополнениях повторите команду с --mode expert. После проверки остановите только эту копию командой docker compose -p booking-review down; данные volume сохранятся.

3. Если нужен живой запуск исходного B02 для видео, в ещё одном клоне выполните git switch --detach STARTER_COMMIT, заменив STARTER_COMMIT хешем из REPORT. Создайте .env с API_PORT=18081 и используйте -p booking-starter во всех командах. Не переключайте исходную рабочую папку с решением на старую версию. После демонстрации остановите копию командой docker compose -p booking-starter down.
4. Откройте страницу своего Fork на GitHub, выберите solution/booking и проверьте, что REPORT, SQL-миграция и submission-results видны в браузере. Откройте видео по ссылке из опубликованного REPORT.

## Передать на проверку

Отправьте ссылку на ветку своего Fork и точный хеш комплекта в канал сдачи, объявленный руководителем семинара. Материалы должны быть доступны обоим экспертам.

По умолчанию сдаётся ссылка. Если на семинаре согласован PR, откройте его из solution/booking своего Fork в исходный репозиторий и добавьте в описание commit, ссылку на REPORT и видео. Эксперты закрывают такой PR без merge. Допустим также PR внутри своего Fork, если этот способ принят на семинаре.

Эксперты независимо запускают тесты и читают решение на одном commit. При расхождении они прикладывают результаты, указывают версию окружения и согласуют баллы по [GRADING](GRADING.md). Изменённые или отключённые исходные тесты не служат основанием для баллов.
