# Практическое задание

Вы получили сервис, который правильно бронирует ресурс при последовательных запросах. Если два клиента обращаются одновременно, он может выдать два удержания или создать две брони. Исправьте удержания и подтверждения, сохранив готовую инфраструктуру. Главное правило: в PostgreSQL должно быть не больше одной подтверждённой брони на ресурс при любом порядке запросов. Далее это правило называется инвариантом.

Ожидаемая подготовка: Python, основы HTTP и SQL; Docker уже установлен и запускается. Предварительное знание Redis не требуется. Вся работа выполняется одним студентом. План обязательной части: **8,5 часа**, включая час резерва на отладку, отчёт и видео. Дополнения занимают ещё **2,5 часа**, общий ориентир 11 часов. Практический диапазон: 8–9 часов для базы и 10,5–12 часов с дополнениями. Это инженерная оценка, пробное прохождение студентом пока не проводилось. Установка Docker с нуля и восполнение основ Python/SQL могут потребовать дополнительного времени.

| Работа | Минуты | Что входит |
|---|---:|---|
| Этап 0 | 75 | Запуск, знакомство с кодом, теория Redis/SQL |
| Этап 1 | 45 | Воспроизведение и фиксация исходных дефектов |
| Этап 2 | 75 | Атомарное удержание |
| Этап 3 | 105 | SQL-миграция и обработка конфликта |
| Этап 4 | 60 | TTL и проверка владельца |
| Этап 5 | 90 | Проверки 30, отчёт 30, видео 30 |
| Резерв | 60 | Сборки, отладка и повторная запись демонстрации |
| Дополнение A | 75 | Безопасное освобождение |
| Дополнение B | 75 | Разбор гонки TTL и предложение усиления |

Обязательное чтение: README, этапы задания, теория, контракт и нужные разделы подготовки/архитектуры. Аналитическая записка, предложение топика и презентация подготовлены для семинара; студенту не нужно писать их заново или включать в отчёт. Результаты тестов можно приложить файлами, переписывать их вручную не требуется.

## Этап 0. Подготовка, 1,25 часа

Цель: разобраться, где хранится временное и постоянное состояние.

Если уже выполнили быстрый пример README, повторять его на занятом ресурсе не нужно: используйте полученную бронь для наблюдений ниже или сначала сбросьте демонстрационные данные командой из конца этапа.

1. Получите свою копию и ветку по [SETUP](SETUP.md#получение-своей-копии). Все команды выполняйте в терминале компьютера из папки с compose.yaml. Python, PostgreSQL и Redis отдельно устанавливать не нужно: они запускаются в контейнерах.
2. Запустите стенд и проверьте его состояние:

```sh
docker compose up --build -d
docker compose ps
docker compose exec app python -m scripts.demo --resource 1
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode smoke
git rev-parse HEAD
```

3. Дождитесь healthy у трёх сервисов. Пример должен вывести два ответа 201 и сохранённую бронь, smoke должен показать S01–S05 как пройденные. Перенесите исходный commit в REPORT. При ошибке подключения сначала проверьте [диагностику](SETUP.md#диагностика).
4. Откройте [архитектуру](ARCHITECTURE.md), [контракт](API_CONTRACT.md) и [теорию](THEORY.md). Удержание временно закрепляет ресурс за клиентом; подтверждённая бронь сохраняет его в PostgreSQL. TTL задаёт срок удержания, holdId обозначает конкретную попытку захвата. Найдите create_hold и confirm в app/service.py, insert_booking и migrate в app/repository.py, таблицы в db/init.sql.
5. Посмотрите данные последовательного примера:

```sh
docker compose exec postgres psql -U booking -d booking -c "SELECT id, resource_id, client_id, hold_id, status FROM bookings;"
docker compose exec redis redis-cli GET booking-lab:hold:1
docker compose exec redis redis-cli PTTL booking-lab:hold:1
```

В SQL должна быть бронь alice для ресурса 1. В Redis до истечения 60 секунд виден JSON с clientId и holdId, PTTL показывает остаток в миллисекундах. После истечения ключ исчезает, PTTL возвращает -2. При изменённых POSTGRES_USER/POSTGRES_DB подставьте свои значения вместо booking.

6. Сохраните наблюдения и bookingId в REPORT, затем очистите только демонстрационные брони и удержания этого стенда:

```sh
docker compose exec app python -m scripts.reset_demo --confirm-local-reset
```

Готово, когда S01–S05 проходят, вы можете получить три ресурса и показать строку брони в SQL. Сохраните вывод и версию commit.

## Этап 1. Воспроизведение, 0,75 часа

Цель: связать наблюдаемый дефект с порядком операций.

1. До исправления кода запустите полный base:

```sh
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode base
```

Ожидаются 9 пройденных проверок, 6 падений и 14/60 функциональных баллов. B02/B03/B04/B06/B07/B08 должны обнаружить исходные дефекты. Ошибка при подготовке окружения (ERROR) требует отдельного разбора; она не заменяет ожидаемое падение проверки (FAILED).

2. Скопируйте в редакторе reports/base-results.json и reports/base-results.md в reports/starter-base-results.json и reports/starter-base-results.md. Следующий запуск режима перезаписывает base-results.*. В REPORT укажите эти файлы и исходный commit.
3. В tests/test_booking.py прочитайте test_concurrent_holds (B02) и test_concurrent_confirm (B06). В tests/helpers.py найдите используемый барьер. Он останавливает двух участников после предварительной проверки, чтобы оба успели дойти до записи. Для отдельного запуска B02 выполните:

```sh
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k test_concurrent_holds
```

4. Нарисуйте в REPORT таблицу «шаг / клиент A / клиент B»: чтение свободного состояния, проверка, запись. Отдельно разберите C по test_expired (B03) и test_ownership (B04): почему одного clientId недостаточно, что происходит с неверным holdId и отсутствующим ключом. Сохраните исходные результаты для видео.

Готово, когда в отчёте есть реальные результаты до исправления и объяснение причины каждого дефекта. Связанные проверки: B02/B03/B04/B06/B07/B08.

## Этап 2. Атомарное удержание, 1,25 часа

Цель: при конкурентном захвате свободного ресурса выдать один действительный токен.

1. Найдите TODO A в BookingService.create_hold. Сохраните проверки существования ресурса и SQL-брони, имя ключа через self.key, UUIDv4 и JSON с clientId/holdId.
2. Объедините условие «ключ отсутствует», запись и TTL одной командой Redis SET с параметрами NX и PX. NX разрешает запись только отсутствующего ключа, PX задаёт срок в миллисекундах. Передайте ttlSeconds × 1000 через метод set Python-клиента; обработайте результат команды. [Справочник SET](https://redis.io/docs/latest/commands/set/).
3. Верните 201 с созданным токеном только при успешной установке. При занятом ключе верните 409 RESOURCE_HELD в формате контракта. Не перезаписывайте чужое удержание и не продлевайте его срок при отказе.
4. Сохраните вызов after_hold_read перед условной записью: он нужен тесту, даже если отдельного GET больше нет. Сохраните файл и запустите:

```sh
docker compose up --build -d
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k 'test_concurrent_holds or test_hold_and_confirm or test_unavailable_resources'
```

Здесь -k выбирает B02, B01 и B10 по именам функций. Тестовый образ собирается из сохранённых файлов, поэтому commit перед каждой проверкой не обязателен. Обычный restart app новые файлы в образ не переносит.

5. В REPORT объясните, как обработаны успех и отказ команды, почему раздельные GET/SET оставляют гонку и почему блокировка в памяти одного процесса не защищает другие процессы.

Готово, когда B02 получает ровно один HTTP 201 и один 409, а фактический токен в Redis совпадает с токеном победителя. B01 и B10 также проходят.

## Этап 3. Подтверждение в PostgreSQL, 1,75 часа

Цель: защитить инвариант независимо от состояния Redis и числа процессов API.

1. Прочитайте [инструкцию по миграциям](MIGRATIONS.md). В задании уже выбран способ обновления БД: последовательные SQL-файлы с реестром schema_migrations. Alembic, отдельный сервис миграций и автоматические откаты настраивать не нужно.
2. Создайте db/migrations/001_booking_resource_unique.sql. Добавьте именованное ограничение уникальности resource_id существующей таблицы bookings. Здесь все брони подтверждены и отмены нет, поэтому ресурс определяет уникальность. Запишите в REPORT, почему добавление client_id или hold_id в набор уникальных колонок нарушило бы это правило.
3. Примените миграцию и проверьте сохранность прежней брони по шагам [MIGRATIONS](MIGRATIONS.md#применение-и-проверка). Сохраните SQL-файл в Git. Не заменяйте миграцию правкой db/init.sql, пересозданием таблиц или очисткой данных в коде миграции.
4. Найдите TODO B в BookingService.confirm и Repository.insert_booking. Запись должна оставаться в транзакции: готовый контекст соединения фиксирует её при успехе и откатывает при исключении. Перехватывайте ожидаемый UniqueViolation после выхода из этого контекста либо обеспечьте эквивалентный корректный откат. [Транзакции psycopg](https://www.psycopg.org/psycopg3/docs/basic/transactions.html).
5. У исключения psycopg.errors.UniqueViolation поле diag.constraint_name содержит имя нарушенного ограничения. Сопоставьте его с именем, заданным в вашей миграции. Только конфликт ресурса преобразуйте в 409 RESOURCE_ALREADY_BOOKED; остальные SQL-ошибки должны дойти до общего обработчика. B08 отдельно создаёт нарушение первичного ключа и ожидает 500. [Диагностика ошибок psycopg](https://www.psycopg.org/psycopg3/docs/api/errors.html#psycopg.errors.Diagnostic.constraint_name).
6. Сохраните before_booking_insert непосредственно перед попыткой SQL-записи, пересоберите приложение и проверьте:

```sh
docker compose up --build -d
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k 'test_repeat or test_concurrent_confirm or test_database_invariant or test_database_conflict_response or test_process_restart'
```

7. Перенесите в REPORT имя ограничения, способ обработки конфликта и результаты B05–B09. Предварительный SELECT можно оставить для раннего ответа; объясните, почему он может устареть и окончательное решение принимает БД.

Готово, когда B05–B09 проходят: конкурентные INSERT не создают дубликат, конфликт возвращает 409, последующие запросы продолжают работать, отдельный процесс видит сохранённую бронь.

## Этап 4. TTL и владение, 1 час

Цель: авторизовать только предъявителя действительного удержания.

1. Найдите TODO C в BookingService.confirm. После проверок существования ресурса и SQL-брони прочитайте Redis-ключ именно запрошенного resourceId. При отсутствии ключа верните 409 HOLD_EXPIRED_OR_INVALID.
2. Сопоставьте сохранённые clientId и holdId с запросом. UUID сравнивайте в одинаковом представлении; модель запроса содержит объект UUID, JSON Redis содержит строку. При любом несовпадении верните ту же ошибку без записи SQL и изменения Redis.
3. Сохраните приоритет ошибок из [контракта](API_CONTRACT.md#подтверждение): уже подтверждённая SQL-бронь даёт RESOURCE_ALREADY_BOOKED до проверки токена. Перенесите after_authorization сразу после успешного сопоставления данных.
4. Считайте удержание действительным на момент чтения совпавшего значения. Если TTL истёк до чтения, запрос отклоняется. Истечение после этого чтения допускает попытку SQL-записи. Отдельный PTTL не связывает Redis с SQL-транзакцией.
5. Сохраните изменения, пересоберите приложение и запустите B03/B04:

```sh
docker compose up --build -d
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k 'test_expired or test_ownership'
```

6. В REPORT укажите момент авторизации и результаты отказов. Проверьте по тестам старый токен после повторного захвата тем же клиентом, токен другого ресурса и отсутствие ключа. Не используйте присланное клиентом время как доказательство срока.

Готово, когда B03/B04 проходят, старый токен не подтверждает новую аренду и не меняет её, а после естественного истечения TTL свободный ресурс доступен следующему клиенту. Связанные проверки: B01/B03/B04.

## Дополнение A. Безопасное освобождение, 1,25 часа

1. Откройте BookingService.release и [контракт DELETE /holds](API_CONTRACT.md#освобождение-дополнение-a). Маршрут и модель запроса уже есть; вместо 501 нужно реализовать логику сервиса.
2. Проверьте существование ресурса. Сравните clientId/holdId и удалите только совпавший ключ одной атомарной операцией, например коротким Lua-скриптом. При несовпадении или отсутствии ключа верните 409 HOLD_EXPIRED_OR_INVALID, при удалении верните 204 без тела. Отдельные GET и DEL оставляют гонку.
3. Вызовите before_release_delete перед атомарной операцией; если есть предварительный GET, вызов должен стоять после него. При наличии SQL-брони разрешается удалить действительное удержание, сама бронь сохраняется.
4. Пересоберите приложение и запустите E01:

```sh
docker compose up --build -d
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k test_release
```

5. В REPORT и видео покажите, как поздний запрос A мог бы удалить новое удержание B, и объясните, почему ваша атомарная операция сохраняет чужой ключ.

E01 проверяет корректное удаление, неверный токен, чужого клиента, старый токен после TTL и подмену удержания непосредственно перед атомарной операцией. Наличие подтверждённой SQL-брони не мешает освободить ещё действующий ключ и не позволяет отменить бронь. Вызовите before_release_delete в месте, указанном в архитектуре. Готово, когда E01 проходит и вы можете объяснить ошибку позднего удаления.

## Дополнение B. TTL между авторизацией и commit, 1,25 часа

1. Прочитайте test_ttl_after_authorization (E02). Клиент A проходит авторизацию и останавливается в контрольной точке; его TTL истекает. B получает новый токен и фиксирует бронь. Затем A продолжает запись и получает конфликт. В единственной SQL-строке должны остаться клиент и токен B.
2. Запустите полный expert; он включает smoke, base, E01 и E02:

```sh
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode expert
```

Ожидается 17 пройденных проверок. Сохраните reports/expert-results.json и .md.

3. В REPORT нарисуйте порядок A / Redis / B / PostgreSQL и отметьте чтение токена, истечение TTL и commit. Объясните, почему одна SQL-бронь сохраняется, хотя временный владелец Redis успел смениться. Разберите и обратный порядок: если раньше записывает уже авторизованный A, уникальность должна отклонить B.
4. Предложите более строгую модель, например хранить аренду в PostgreSQL и проверять её в той же транзакции под блокировкой. Укажите, что это меняет в гарантиях, как влияет на нагрузку, очистку/продление и обработку повторов. Достаточно обоснованного проекта; внедрять его в сервис для этого дополнения не требуется.
5. Покажите результат и объясните границу гарантии в видео. Уровень Э требует обоих дополнений и всех условий П; одних зелёных E01/E02 недостаточно.

Готово, когда E02 проходит, есть диаграмма и технически обоснованное предложение с ограничениями. Эксперт проверяет объяснение вручную.
