# Как добавить SQL-миграцию

Миграция меняет уже существующую схему БД. В этом задании она должна запретить две подтверждённые брони одного ресурса и сохранить корректные записи.

## Какой способ использовать

Способ уже выбран: SQL-файлы в db/migrations, которые применяет Repository.migrate из app/repository.py. Он выполняется при старте приложения и при запуске scripts.migrate. Файлы сортируются по имени; имена выполненных файлов записываются в таблицу schema_migrations. Обновление проходит в транзакции.

Используйте этот механизм. Настройка Alembic, Flyway, отдельного сервиса миграций, миграций без остановки сервиса и обратных миграций в задание не входит. Контроль версий обеспечивает Git: SQL-файл нужно сохранить в том же репозитории, что и код.

## Подготовить файл

1. Откройте db/init.sql. В bookings каждая запись имеет статус CONFIRMED, отмен нет. Поэтому уникальным должен быть resource_id: разные клиенты и токены не дают права на вторую бронь того же ресурса.
2. В редакторе создайте файл db/migrations/001_booking_resource_unique.sql с кодировкой UTF-8. Если вы уже создали миграцию под другим именем, используйте её; второй файл с тем же ограничением не нужен.
3. Добавьте SQL-команду ALTER TABLE, которая создаёт именованное ограничение UNIQUE для resource_id в bookings. Имя выберите сами, например bookings_resource_unique; оно понадобится при обработке исключения. Синтаксис смотрите в документации [ALTER TABLE](https://www.postgresql.org/docs/16/sql-altertable.html) и [ограничений](https://www.postgresql.org/docs/16/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS).
4. Обращайтесь к bookings без префикса public: тесты задают свою схему через search_path. Не добавляйте создание или удаление БД, DROP/TRUNCATE таблиц, удаление броней и собственные BEGIN/COMMIT. Транзакцией управляет готовый Python-код.

Правка только db/init.sql не обновит существующую таблицу, созданную через CREATE TABLE IF NOT EXISTS. Обязательный результат этого этапа включает отдельный файл миграции.

## Применение и проверка

Команды выполняйте из корня проекта. Значения booking ниже соответствуют стандартным POSTGRES_USER и POSTGRES_DB. Если изменяли .env, подставьте свои значения.

1. Перед применением запишите в REPORT существующие брони и проверьте дубликаты:

```sh
docker compose exec postgres psql -U booking -d booking -c "SELECT id, resource_id, client_id, hold_id, status, created_at FROM bookings ORDER BY resource_id;"
docker compose exec postgres psql -U booking -d booking -c "SELECT resource_id, count(*) FROM bookings GROUP BY resource_id HAVING count(*) > 1;"
```

Если bookings пуста, создайте одну бронь последовательным примером из README и сохраните bookingId. Для проверки обновления нужна хотя бы одна прежняя запись.

2. Если второй запрос нашёл дубликаты, сначала сохраните наблюдение. Уникальное ограничение не сможет примениться к таким данным. Для одноразового учебного стенда разрешается осознанно очистить демонстрационные данные по [SETUP](SETUP.md#изменения-и-данные), затем создать одну корректную бронь. Не включайте очистку в миграцию: у проверяющего существующая контрольная запись должна сохраниться.
3. Сохраните SQL-файл и пересоберите приложение:

```sh
docker compose up --build -d
docker compose ps
docker compose logs --tail=50 app
```

Исходники копируются в образ при сборке. Обычный restart не добавляет новый файл. При старте нового образа приложение само вызывает migrate. Если старт прервался из-за SQL, исправьте синтаксис или разберите дубликаты, затем повторите сборку. Если app циклически перезапускается, используйте порядок восстановления из SETUP.

4. После успешного запуска проверьте реестр и определение таблицы:

```sh
docker compose exec postgres psql -U booking -d booking -c "SELECT name FROM schema_migrations ORDER BY name;"
docker compose exec postgres psql -U booking -d booking -c "\d bookings"
docker compose exec postgres psql -U booking -d booking -c "SELECT id, resource_id, client_id, hold_id, status, created_at FROM bookings ORDER BY resource_id;"
```

В реестре должно быть имя вашего файла, в таблице должно появиться ограничение UNIQUE для resource_id. Прежняя бронь должна сохранить все поля. Добавление primary key по id уже было в заготовке и не решает задачу ресурса.

5. Проверьте повторный запуск механизма:

```sh
docker compose exec app python -m scripts.migrate
docker compose exec postgres psql -U booking -d booking -c "SELECT name FROM schema_migrations ORDER BY name;"
```

Команда должна закончиться сообщением «Схема и миграции применены» без повторного добавления ограничения. В реестре остаётся одна строка на файл. Не требуйте от SQL-файла самостоятельной повторяемости: повторное применение предотвращает реестр.

6. Запустите B07, который проверяет обновление исходной схемы с контрольной бронью и уникальность при прямых конкурентных INSERT:

```sh
docker compose --profile test run --build --rm tests python -m pytest -q tests/test_booking.py -k test_database_invariant
```

После обработки конфликта в confirm выполните также B06/B08 и полный base по [заданию](ASSIGNMENT.md#этап-3-подтверждение-в-postgresql-175-часа). Успех B07 сам по себе не подтверждает правильный HTTP-ответ сервиса.

## Если нужно изменить миграцию

Пока файл не применён успешно, исправляйте его и повторяйте сборку. Если его имя уже есть в schema_migrations, механизм не запустит изменённое содержимое повторно. Для следующего изменения добавьте файл с новым номером, например 002_adjust_constraint.sql. Не удаляйте строки реестра для обхода этого правила.

В REPORT укажите имена файлов, имя ограничения, команды и сохранность прежней брони. В Git должны попасть SQL-файлы и код обработки конфликта. PostgreSQL volume, .env и содержимое БД в Git не добавляются.
