# Конкурентное бронирование: где заканчиваются гарантии хранилища

## Актуальность проблемы

Сервис бронирования обещает пользователю конкретный результат: выбранное место закреплено за ним. Нарушение этого обещания видно за пределами программы. Двум посетителям придётся делить один билет, оператору склада потребуется разбирать конфликт, а службе поддержки объяснять, какой ответ сервера считать действительным. Поэтому конкурентная корректность относится к требованиям продукта, даже если ошибка возникает редко и приложение почти всегда отвечает быстро.

В небольшом проекте соблазнительно сначала прочитать состояние, затем выполнить запись. Такой код понятен при последовательном чтении. Разработчик запускает один запрос, получает ожидаемый ответ и считает сценарий завершённым. Но сервер обслуживает несколько клиентов, процессы приостанавливаются на сетевых вызовах, а ответы хранилищ описывают состояние в разные моменты. Проверка одного запроса не исследует эти пересечения. Учебный пример позволяет рассмотреть их без платежей, интеграций и других деталей реального продукта.

В топике используется одноразовое бронирование отдельных ресурсов. У этой модели есть ясный инвариант: одному ресурсу соответствует не больше одной подтверждённой записи. Он достаточно прост для автоматической проверки и при этом обнаруживает ошибки, которые не видны в обычном успешном запросе. Студент должен связать обещание HTTP API с ограничениями SQL и временем жизни ключа Redis.

## Природа конкурентных ошибок

Главный дефект исходного сервиса относится к check-then-act. Клиент A проверяет отсутствие удержания. До его записи клиент B получает такой же ответ. Затем оба записывают свои токены и оба получают HTTP 201. Redis хранит последнее значение, но первый клиент уже получил ложное обещание успеха. Каждая команда хранилища могла выполниться корректно: нарушен порядок составной операции приложения.

Похожая ошибка возникает при подтверждении. Две транзакции отдельно проверяют отсутствие строки и вставляют бронь. Наличие транзакции вокруг каждого INSERT само по себе не выражает запрет второй записи. Требование нужно сформулировать в терминах общего состояния, доступного обоим участникам. Локальный mutex защищает только потоки конкретного процесса и перестаёт быть достаточным при втором экземпляре API или прямом SQL-доступе.

Нагрузочное тестирование способно обнаружить подобные дефекты, но случайная нагрузка плохо подходит для первого знакомства. Студенту трудно понять, исчезла ли ошибка после исправления или просто не возник нужный порядок. В задании барьер приостанавливает обе операции после предварительной проверки. Такой тест фиксирует порядок, который приводит к ошибке. Он не доказывает корректность всех возможных исполнений, поэтому его дополняет чтение SQL-ограничения и объяснение алгоритма.

## Подходы PostgreSQL

PostgreSQL подходит для хранения окончательного результата, поскольку инвариант можно описать ограничением таблицы. В модели без отмен уникальность ресурса запрещает две строки независимо от того, какой клиент выполняет INSERT. База проверяет это правило и при конкурентных транзакциях. Уникальный индекс учитывает конфликтующие незавершённые изменения; конкурирующая операция может ждать исхода другой транзакции, затем получить нарушение уникальности. Это сильнее предварительного запроса приложения. [Ограничения](https://www.postgresql.org/docs/16/ddl-constraints.html), [проверка уникальности](https://www.postgresql.org/docs/16/index-unique-checks.html).

Для API такое нарушение относится к ожидаемому результату соперничества. Оно должно превращаться в конфликт, а не в успешный ответ или необъяснённую внутреннюю ошибку. При этом обработчик не должен называть конфликтом синтаксическую ошибку SQL или отказ соединения. Проверка причины исключения сохраняет различие между бизнес-результатом и неисправностью сервиса.

Транзакция задаёт границу фиксации SQL. Ответ об успешной брони отправляется после commit. Если запись не удалась, изменения откатываются; дальнейшая работа не должна продолжаться в прерванной транзакции. Важно также учитывать область ограничения: если позже появятся отменённые брони и история повторных продаж, безусловная уникальность ресурса перестанет соответствовать предметной модели. Тогда потребуется заново определить допустимые состояния. [Транзакции PostgreSQL](https://www.postgresql.org/docs/16/tutorial-transactions.html).

## Подходы Redis

Redis решает другую задачу: временно ограничивает соперничество до долговременного подтверждения. Удержание содержит случайный токен и метку клиента, а TTL освобождает ресурс, если клиент исчез. Условная установка ключа с NX и PX объединяет проверку отсутствия, запись и назначение срока. Только один конкурент получает успешный результат этой команды для одного отсутствующего ключа. [SET](https://redis.io/docs/latest/commands/set/).

Секретный токен нужен независимо от атомарности установки. Имя клиента не обладает достаточной доказательной силой: его можно повторить в другом запросе. Более того, один и тот же клиент может получить новую аренду после истечения старой. Сравнение UUID удержания позволяет различить эти два поколения владения. Сервис должен проверить одновременно ресурс, клиента и токен по действительному значению хранилища.

TTL требует аккуратной интерпретации. Значение в успешном HTTP-ответе сообщает исходную длительность, но часть времени уже потрачена на выполнение и сеть. Клиент не получает обещание, что после получения ответа осталось ровно столько секунд. Сервер ориентируется на существование ключа при проверке. Команда PTTL помогает исследовать состояние, но сама по себе не подтверждает владельца. [PTTL](https://redis.io/docs/latest/commands/pttl/), [срок действия ключей](https://redis.io/docs/latest/commands/expire/).

## Проблемы согласованности

Самая существенная граница проходит между успешной проверкой удержания и фиксацией SQL. Redis не участвует в транзакции PostgreSQL, а SQL commit не удерживает ключ Redis от истечения. Повторная проверка ближе к INSERT уменьшает окно, но следующий сетевой вызов снова оставляет время для изменения состояния. Нельзя вывести общую атомарность процесса из атомарности отдельных его шагов.

Поэтому контракт задания разделяет проверку срока, авторизацию и commit. Если Redis уже считает удержание истёкшим при чтении, авторизация запрещена. Если прочитанное значение действительно и совпадает с предъявленными данными, логическая точка авторизации находится в момент этого чтения. Последующее сравнение в Python подтверждает принятое решение. После чтения совпавшего значения истечение TTL не отменяет автоматически начатую запись. Такая семантика выбрана для этого учебного сервиса.

Разделение позволяет поставить проверяемую задачу. Студент обязан отклонять давно истёкший токен и защищать SQL-инвариант при любом исходе соперничества. От него не требуется распределённая транзакция. Требование актуальности именно на момент commit означало бы другой контракт и другую архитектуру. При обсуждении решения эксперт должен проверить, на какой момент времени автор гарантирует действительность токена.

## Пример сервиса бронирования

Рассмотрим клиента A, который получил удержание и успешно прошёл авторизацию подтверждения. Затем его выполнение остановилось. TTL истёк, B захватил тот же ресурс и также прошёл авторизацию. Теперь оба запроса имеют основания продолжить SQL-операцию по принятому контракту. Если первым фиксируется B, поздний INSERT A получает конфликт уникальности. В PostgreSQL остаётся одна бронь, хотя во времени существовали два разных разрешения на попытку подтверждения.

Другой порядок также допустим: A возобновляется раньше и успевает записать бронь до B. К этому моменту Redis уже может хранить токен B. Это неудобный пользовательский результат, но он не противоречит принятой точке авторизации. Задание разделяет анализ такого результата и проверку отсутствия дубликатов. Удержание B уже не позволит ему подтвердить занятой ресурс, а в SQL сохранится одна бронь.

Возможна и более короткая остаточная гонка. B проверил в PostgreSQL отсутствие брони, A успел зафиксировать результат, а B после этого установил удержание в Redis. Ответ на захват оказался временно устаревшим относительно SQL. Проверка существующей брони или окончательное ограничение при подтверждении не позволят B записать вторую строку. Для продукта можно улучшать согласованность ответа на захват, но это отдельное обещание, требующее отдельного доказательства.

## Ограничения решений

Даже правильная защита от дубликатов не даёт полной семантики повторных запросов. Процесс может зафиксировать бронь и потерять соединение до HTTP-ответа. Пользователь не знает, произошло ли действие. В учебном контракте повторное подтверждение возвращает конфликт, а сохранённую бронь можно прочитать отдельно по известному идентификатору. Более удобный публичный API потребовал бы идемпотентного ключа запроса или способа восстановить результат по доступным клиенту данным. Такое расширение не следует смешивать с устранением первой гонки.

Освобождение удержания тоже содержит конкурентную проблему. A прочитал свой токен, затем задержался. Ключ истёк, B получил новый. Безусловный DEL от A удалит уже чужой ключ. Нужна атомарная операция сравнения и удаления. Короткий Lua-скрипт Redis позволяет выполнить её относительно других команд без промежуточного окна. Однако такой скрипт всё равно не управляет SQL-транзакцией. [Lua в Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/).

Один из способов усилить общую модель состоит в хранении аренды и брони в PostgreSQL, с проверкой одной строки внутри той же транзакции. Тогда состояние, необходимое для решения, находится у одного координатора. Цена включает дополнительную нагрузку от удержаний и продлений, правила очистки и ожидание блокировок. Внешний Redis может остаться кэшем, но источником окончательного разрешения станет SQL. Выбор зависит от требований, а не от предположения, что больше хранилищ автоматически повышает надёжность.

## Выводы

Для защиты бронирования сначала нужно назвать инвариант и момент принятия решения. В предложенной работе Redis отвечает за временный захват, а PostgreSQL запрещает повторное подтверждение. Токен связывает запрос с конкретным удержанием. Эти роли дополняют друг друга, но не образуют общую транзакцию.

Учебная ценность примера состоит в сопоставлении кода с наблюдаемым порядком операций. Студент получает воспроизводимый контрпример, исправляет небольшой участок и проверяет реальное состояние двух хранилищ. Затем объясняет, какое обещание теперь выполняется и какая граница осталась. Такой разбор полезнее заявления об абсолютной безопасности, которого выбранная архитектура не может обосновать.
