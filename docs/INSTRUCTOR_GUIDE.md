# Регламент экспертов

Публичные заметки описывают ожидаемые гарантии и проверку, без полного кода решения. Работу проверяют два эксперта по [шкале](GRADING.md) на одном commit.

## Ожидаемые подходы

A: одна условная установка Redis с TTL и проверкой результата. Один вызов с NX/PX заменяет раздельные check/set; синхронизация Python не подходит как защита при нескольких процессах.

B: PostgreSQL запрещает вторую строку ресурса ограничением уникальности; транзакция корректно завершается/откатывается. Проверяйте имя или назначение ограничения при преобразовании UniqueViolation в конфликт. Прямой SQL B07 исключает ложное решение только на уровне приложения. Полная выдача исправленной реализации в starter недопустима.

C: действительный ключ сопоставляется одновременно с ресурсом, клиентом и токеном; отсутствие ключа даёт отказ. UUID другого ресурса или прежней аренды не должен работать, даже если новую аренду получил тот же клиент. TTL оценивается на момент чтения совпавшего значения в Redis, без требования общей транзакции Redis/SQL.

Дополнение A: короткая атомарная операция сравнения/удаления. Проверьте E01 и место контрольной точки. Дополнение B: E02 задаёт порядок B commit перед A insert. A получает конфликт, в SQL остаётся B. Анализ должен объяснять и другой допустимый порядок, когда первым фиксируется ранее авторизованный A.

## Порядок проверки

1. Прочитайте REPORT и проверьте доступ к видео, зафиксируйте commit.
2. В отдельной копии выполните запуск и smoke. Затем base, для Э expert. Сохраните собственные результаты отдельно от студенческих.
3. Проверьте миграцию на существующей БД: сначала создайте таблицы starter, затем запустите образ решения с тем же volume. Если там есть специально полученные дубликаты, сначала обсудите их очистку; миграция не обязана угадывать, какая из ошибочных броней правильна.
4. Посмотрите реальное ограничение и остаточное состояние SQL/Redis. Проверьте, что нет маршрутов управления барьерами и ветвления по тестовым именам.
5. Сопоставьте объяснение автора с кодом. Нельзя присваивать Э только по двум зелёным строкам expert.
6. Заполните баллы независимо. Расхождения обсудите по конкретным пунктам, итоговый PR закройте без merge.

## Перед публикацией топика

Проверьте на втором компьютере команды README, доступность закреплённых образов и время первого скачивания. Бюджет задания: 7,5 часа этапов и час резерва, ещё 2,5 часа на дополнения. Ожидаемые 8–9 часов для базы и 10,5–12 часов с дополнениями рассчитаны на студента с основами Python/SQL и работающим Docker; знание Redis заранее не требуется. Это инженерная оценка, которую нужно уточнить пробным прохождением. Установка Docker с нуля и обучение основам Python/SQL в бюджет не входят. Назначьте двух экспертов и фактический адрес сдачи. Не публикуйте локальный каталог .instructor, .env, отчёты разработчика и Docker volumes. Проверьте git ls-files: .instructor не должен попасть в индекс даже при наличии локальных эталонных материалов.

Фактические результаты проверки подготовленного проекта находятся в [VALIDATION](VALIDATION.md). После любых изменений инфраструктуры повторите smoke; после изменений тестов убедитесь, что starter по-прежнему обнаруживает дефекты и корректная реализация удовлетворяет требованиям.
