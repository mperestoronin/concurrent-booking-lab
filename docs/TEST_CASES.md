# Сценарии и запуск проверок

Источник весов: tests/cases.json. scripts/check_repository.py сверяет ID и баллы таблицы с manifest и тестами.

| ID | Режим | Требование и сценарий | Ожидаемый результат | Баллы |
|---|---|---|---|---:|
| S01 | smoke | Реальные хранилища, отказ клиента и ошибка команды Redis | 200 при доступности, 503 при отказе, 500 при ошибке команды | 0 |
| S02 | smoke | Чтение seed | Свободные ресурсы 1, 2, 3 | 0 |
| S03 | smoke | Последовательная бронь, чтение SQL и GET | 201; одна строка, совпадающий GET | 0 |
| S04 | smoke | Плохие поля, JSON и UUID; границы TTL; неверный метод | 422/404/405 с единым error; Allow; TTL 1 и 60 допустимы | 0 |
| S05 | smoke | OpenAPI, схема ошибок и попытка вызвать debug | Документирован ErrorResponse, только заданные пути, debug=404 | 0 |
| B01 | base | Захват и подтверждение, чтение Redis/SQL | UUIDv4, TTL>0; SQL содержит токен и клиента | 4 |
| B02 | base | Два захвата на барьере перед записью | 201+409, в Redis токен победителя, SQL пуст | 10 |
| B03 | base | Истечение Redis и повторная аренда другим и тем же клиентом | Старому токену 409, новому 201, новый ключ сохранён | 6 |

| B05 | base | Дважды подтвердить один токен | 201, затем 409, одна строка SQL | 4 |

**Итого обязательной функциональности: 60 баллов.** Smoke и дополнения баллов не добавляют. Expert служит условием уровня Э.

## Команды

```sh
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode smoke
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode base
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode expert
```

base включает smoke, expert включает smoke и base. Ненулевой exit code означает непройденную проверку, даже если часть баллов набрана. Текст и JSON находятся в reports/&lt;mode&gt;-results.*; новый запуск режима перезаписывает его файлы. Скопируйте исходные результаты перед исправлениями.

## Воспроизводимость и изоляция

Тесты отправляют HTTP-запросы через ASGI TestClient к настоящему FastAPI и обращаются к реальным PostgreSQL/Redis. B02 и B06 используют два потока и барьер, B08 создаёт настоящий конкурирующий commit и нарушение первичного ключа, B07 работает вообще без сервиса. Один HTTP-код не доказывает целостность БД. B09 запускает отдельные процессы Python для чтения сохранённой брони. В S01 только проверки отказов подменяют метод клиента исключением соответствующей библиотеки; успешный запрос проверяет настоящие хранилища.

Изолированная SQL-схема создаётся по снимку исходной версии tests/fixtures/starter_schema.sql. До миграций в неё записывается контрольная бронь, которая должна сохраниться после обновления. Затем каждый сценарий начинает с пустой таблицы bookings. Это позволяет B07 обнаружить отсутствие миграции даже при изменённом db/init.sql. Схема удаляется в finally; Redis очищается только по случайному префиксу. FLUSHALL/FLUSHDB нет. Не используйте pytest-xdist: один запуск использует общую SQL-схему, рассчитанную на последовательные сценарии.

В тесте TTL сначала создаётся обычное удержание, затем PEXPIRE сокращает ожидание до десятков миллисекунд. Проверка ждёт реального отсутствия ключа, без подмены часов и фиктивного nil. Таймауты ограничивают ожидание барьеров; PGOPTIONS тестового контейнера ограничивает SQL-команды 15 секундами и ожидание блокировок 10 секундами. Произвольное бесконечное вычисление в студенческом Python-коде этим не ограничивается.

## Исходная точка

Smoke проходит. В base намеренно падают B02/B03/B04/B06/B07/B08. B01/B05/B09/B10 работают уже в последовательном сценарии и дают 14/60. E01 падает из-за заготовки 501; E02 обнаруживает отсутствие окончательной SQL-защиты. Падения нельзя скрывать xfail или начислением баллов за ожидаемую ошибку.

Раннер не начисляет баллы за skip, ошибки setup/teardown и неисполненный сценарий. Smoke сообщает 0/0 и отдельно показывает каждый ID. Вывод не заменяет оценку из 100: видео, отчёт и код оценивают эксперты.

Для запуска без Compose нужны Python 3.12, requirements и явно заданные TEST_DATABASE_URL, TEST_REDIS_URL. Пользователю SQL нужно право создавать тестовые схемы. Отсутствующие настройки дают явную ошибку, без пропуска тестов.

Состав base/expert раннер выбирает по полю mode в manifest, независимо от имён функций. Собственные тесты размещайте в tests/student и запускайте отдельно по [заданию](ASSIGNMENT.md). Они не добавляют сценарии и баллы в штатный раннер.

## Перезапуск контейнера

Сохраните bookingId успешного примера, выполните docker compose restart app, дождитесь healthy и повторите GET /bookings/&lt;bookingId&gt;. Должны вернуться прежние данные. B09 проверяет процессы, этот шаг дополнительно проверяет сохранность volume и настройки контейнера.
