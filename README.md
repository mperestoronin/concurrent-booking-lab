# Конкурентное бронирование: PostgreSQL и Redis

Два клиента пытаются забронировать одно место. Каждый запрос выглядит правильным, но вместе они могут создать две подтверждённые брони. В этом задании нужно воспроизвести ошибку и исправить готовый сервис.

Это **учебная заготовка с намеренными дефектами A, B и C**. Она запускается и выполняет последовательное бронирование. В документах и отчётах исходная версия называется starter. Часть тестов base должна падать, пока вы не исправите конкурентный доступ.

Вы научитесь временно удерживать ресурс в Redis, проверять токен владельца и запрещать повторную бронь ограничением PostgreSQL. Тесты помогут воспроизвести ошибки при заданном порядке запросов. Обязательная часть рассчитана на 8,5 часа, включая отчёт, видео и час резерва на отладку; дополнения занимают 2,5 часа. Нужны основы Python, HTTP, SQL и установленный работающий Docker; Redis можно изучить по [теории](docs/THEORY.md). Подробная [разбивка времени](docs/ASSIGNMENT.md) учитывает все этапы. Аналитическая записка и слайды уже подготовлены для семинара, студенту не нужно создавать их заново.

## Запуск за несколько минут

Нужны Git и Docker с Compose v2 (или совместимой новой версией): Docker Desktop для Windows/macOS либо Docker Engine с плагином Compose для Linux. Ориентир для стенда: 2 CPU, 4 ГБ доступной памяти и 3 ГБ диска. Python на хосте не требуется.

Сначала [создайте Fork и клонируйте его](docs/SETUP.md#получение-своей-копии). Из корня своей копии репозитория выполните:

```sh
docker compose up --build -d
docker compose ps
```

Дождитесь статуса healthy у трёх сервисов. Откройте [документацию API](http://127.0.0.1:8080/docs) или [проверку готовности](http://127.0.0.1:8080/health). PostgreSQL и Redis доступны в сети Compose, их порты на хост не публикуются. .env необязателен; настройки можно скопировать из [.env.example](.env.example).

На свежем стенде выполните готовый пример. Он сам получает токен, подтверждает бронь ресурса 1 и читает её:

```sh
docker compose exec app python -m scripts.demo --resource 1
```

Ожидаются два ответа HTTP 201, затем сохранённая бронь с полями bookingId, resourceId: 1, status: CONFIRMED. Скопируйте bookingId для проверки перезапуска. UUID создаются при каждом запросе, заранее заданных токенов нет. Для ручных запросов используйте /docs: выберите маршрут, нажмите Try it out, заполните JSON по [контракту](docs/API_CONTRACT.md) и нажмите Execute. Пример запросов из PowerShell есть в [SETUP](docs/SETUP.md#запросы-на-windows).

Для повторной демонстрации удалите только учебные брони и удержания:

```sh
docker compose exec app python -m scripts.reset_demo --confirm-local-reset
```

## Что требуется сделать

Выполняйте этапы по порядку. Команды ниже запускаются из папки проекта, где лежит compose.yaml. Сохраняйте результаты по мере работы в [REPORT.md](REPORT.md). Полные требования каждого этапа находятся в [задании](docs/ASSIGNMENT.md).

### 1. Получить свою копию и проверить запуск

1. Создайте Fork репозитория в своём аккаунте GitHub, клонируйте его и создайте ветку solution/booking. Fork хранит вашу работу на GitHub, клон позволяет менять её на компьютере. [Команды и установка инструментов](docs/SETUP.md#получение-своей-копии).
2. Выполните команды запуска выше. Дождитесь healthy у app, postgres и redis; откройте /docs. Если запуск не удался, сначала разберите ошибку по [инструкции](docs/SETUP.md#диагностика).
3. Выполните последовательный пример и smoke. Smoke должен пройти все пять проверок ещё до исправлений. Запишите исходный commit командой git rev-parse HEAD и перенесите его в REPORT.

### 2. Воспроизвести ошибки до изменений

1. Запустите base из раздела «Проверки» ниже. В исходной версии ожидаются падения B02/B03/B04/B06/B07/B08; это ошибки, которые предстоит исправить.
2. В редакторе скопируйте reports/base-results.json и .md под именами starter-base-results.json и .md в той же папке. Следующий запуск base перезапишет исходные файлы.
3. Откройте app/service.py и tests/test_booking.py. Для A и B запишите порядок действий двух клиентов, при котором оба успевают пройти проверку до записи. Для C укажите, какие неверные токены принимает заготовка. [Подробности этапа](docs/ASSIGNMENT.md#этап-1-воспроизведение-075-часа).

### 3. Исправить захват в Redis

1. В BookingService.create_hold замените раздельные проверку и запись на условную атомарную установку ключа с TTL. Сохраните имя ключа, JSON с clientId/holdId и случайный UUIDv4.
2. Если ключ занят, верните ошибку RESOURCE_HELD с HTTP 409. Контрольная точка after_hold_read должна оставаться перед попыткой записи. [Требования и команда проверки](docs/ASSIGNMENT.md#этап-2-атомарное-удержание-125-часа).
3. Сохраните файл, выполните docker compose up --build -d и повторите B02. Ожидаются один успешный захват, один отказ и токен победителя в Redis.

### 4. Защитить подтверждение в PostgreSQL

1. Создайте в редакторе файл db/migrations/001_booking_resource_unique.sql. В нём добавьте именованное ограничение уникальности ресурса в существующей таблице bookings. Схему и корректные брони нужно сохранить.
2. Используйте готовый механизм проекта: он применяет SQL-файлы по имени и записывает их в schema_migrations. Настраивать Alembic, отдельную систему версий БД или откат миграций не требуется. Файл миграции сохраните в Git вместе с кодом. [Порядок применения и проверки](docs/MIGRATIONS.md).
3. В BookingService.confirm обработайте нарушение именно добавленного ограничения как RESOURCE_ALREADY_BOOKED с HTTP 409. Сохраните транзакцию Repository.insert_booking; остальные ошибки SQL не превращайте в конфликт ресурса.
4. Пересоберите приложение и проверьте B05–B09. При конкурентных подтверждениях и прямом SQL должна сохраняться одна бронь. [Пошаговый разбор](docs/ASSIGNMENT.md#этап-3-подтверждение-в-postgresql-175-часа).

### 5. Проверить срок и владельца удержания

1. В BookingService.confirm отклоняйте отсутствующий ключ, чужого клиента и несовпадающий holdId. Читайте ключ запрошенного ресурса. Старый токен не должен подтверждать новое удержание даже у того же клиента.
2. Проверяйте действительность на момент чтения Redis. Истечение TTL после успешной авторизации разбирается отдельно; общей транзакции двух хранилищ здесь нет.
3. После пересборки запустите B03/B04 и полный base. Ожидаются отказ неверным токенам без изменения данных и 60/60 функциональных баллов после всех исправлений. [Команды и критерии](docs/ASSIGNMENT.md#этап-4-ttl-и-владение-1-час).

### 6. Выбрать дополнения и сдать работу

1. Для уровня Э выполните оба дополнения: безопасный DELETE /holds и разбор гонки TTL между авторизацией и SQL commit. [Требования к дополнениям](docs/ASSIGNMENT.md#дополнение-a-безопасное-освобождение-125-часа).
2. Сохраните итоговый base, для Э также expert. Проверьте чтение прежней брони после docker compose restart app. Заполните REPORT реальными результатами, объяснениями и затраченным временем.
3. Запишите видео на 3–6 минут по [сценарию](docs/SUBMISSION.md#сценарий-видео), загрузите его и проверьте доступ по ссылке. Сохраните код и миграцию в Git, отправьте свою ветку в Fork.
4. Передайте проверяющим ссылку на Fork и commit, REPORT, результаты до/после и видео. [Команды Git и комплект сдачи](docs/SUBMISSION.md). По умолчанию достаточно ссылки; PR нужен, если такой способ согласован на семинаре.

## Как оценивается работа

Итог ставится буквенным уровнем. Для проверки мы буем использовать внутреннюю шкалу из 100 баллов: функциональность 60, видео 25, отчёт 10, качество кода 5.

| Уровень | Что требуется |
|---|---|
| Б− | 60–64 балла, работает B01, доступны заполненный отчёт и видео; оставшиеся ошибки перечислены |
| Б | 65–74 балла с теми же обязательными условиями |
| Б+ | 75–89 баллов; это также предел при 90+ без полного base или без 20/25 за видео |
| П | 90–100 баллов, все B01–B10 проходят (60/60), за видео не меньше 20/25 |
| Э | Все условия П, проходят E01/E02, оба дополнения верно объяснены в отчёте и видео |

Без работающего B01, доступного видео или заполненного отчёта работу нужно дополнить. Дополнения не дают баллов сверх 100. Содержание каждого критерия, частичные баллы и порядок определения уровня описаны в [GRADING.md](docs/GRADING.md).

## Проверки

```sh
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode smoke
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode base
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode expert
```

smoke проверяет каркас и проходит до исправлений. base включает smoke и 10 обязательных сценариев на **60 баллов**. expert включает оба набора и два дополнительных сценария без добавочных баллов. Падение теста даёт ненулевой код выхода. Результаты сохраняются в reports/&lt;mode&gt;-results.json и .md. Тесты используют реальные PostgreSQL/Redis, отдельную SQL-схему и случайные префиксы ключей. Демонстрационные данные приложения они не удаляют. Подробнее: [сценарии](docs/TEST_CASES.md).

Полное выполнение обязательной части: все B01–B10 проходят, в БД остаётся одна бронь при гонке, неверные и истёкшие токены отклоняются, перезапуск API сохраняет данные. Частично выполненная работа оценивается по таблице уровней выше.
