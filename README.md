# Конкурентное бронирование: PostgreSQL и Redis

Два клиента пытаются забронировать одно место. Каждый запрос выглядит правильным, но вместе они могут создать две подтверждённые брони. В этой лабораторной нужно воспроизвести ошибку и исправить готовый сервис.

Это **учебный starter с намеренными дефектами A, B и C**. Он запускается и выполняет последовательное бронирование. Часть тестов base должна падать, пока вы не исправите конкурентный доступ. Полного решения в публичных файлах нет.

За работу вы научитесь создавать удержания Redis с TTL, проверять токены владения, защищать инвариант ограничением PostgreSQL и исследовать проверки с управляемым порядком операций. Обязательная часть рассчитана на 8,5 часа, включая час резерва на отладку; дополнения на 2,5 часа. Нужны основы Python, HTTP, SQL и установленный работающий Docker; Redis можно изучить по [теории](docs/THEORY.md). Подробная [разбивка времени](docs/ASSIGNMENT.md) учитывает отчёт и видео. Аналитическая записка и слайды уже подготовлены для семинара, студенту не нужно создавать их заново.

## Запуск за несколько минут

Нужны Git и Docker с Compose v2 (или совместимой новой версией): Docker Desktop для Windows/macOS либо Docker Engine с плагином Compose для Linux. Ориентир для стенда: 2 CPU, 4 ГБ доступной памяти и 3 ГБ диска. Python на хосте не требуется.

Из корня своей копии репозитория выполните:

```sh
docker compose up --build -d
docker compose ps
```

Дождитесь статуса healthy у трёх сервисов. API: <http://127.0.0.1:8080/docs>, проверка готовности: <http://127.0.0.1:8080/health>. PostgreSQL и Redis доступны в сети Compose, их порты на хост не публикуются. .env необязателен; настройки можно скопировать из [.env.example](.env.example).

```sh
curl http://127.0.0.1:8080/resources
curl -X POST http://127.0.0.1:8080/holds -H 'Content-Type: application/json' -d '{"resourceId":1,"clientId":"alice","ttlSeconds":60}'
```

Скопируйте holdId из ответа и в течение 60 секунд подставьте его вместо UUID_ИЗ_ОТВЕТА:

```sh
curl -X POST http://127.0.0.1:8080/bookings -H 'Content-Type: application/json' -d '{"resourceId":1,"clientId":"alice","holdId":"UUID_ИЗ_ОТВЕТА"}'
```

Ожидаемый ответ: HTTP 201, поля bookingId, resourceId: 1, status: "CONFIRMED". UUID создаются при каждом запросе, заранее заданных токенов нет. Автоматический вариант того же примера:

```sh
docker compose exec app python -m scripts.demo --resource 2
```

Для повторной демонстрации удалите только учебные брони и удержания:

```sh
docker compose exec app python -m scripts.reset_demo --confirm-local-reset
```

## Что делать

1. Пройдите [этапы задания](docs/ASSIGNMENT.md) и запустите исходные проверки.
2. Исправьте A/B/C в app/service.py, добавьте SQL-миграцию в db/migrations/. Сохраняйте контракт и контрольные точки тестов.
3. Пересоберите приложение, запустите base, объясните результаты в [REPORT.md](REPORT.md).
4. При желании выполните освобождение удержания и исследование TTL.
5. Запишите видео 3–6 минут и сдайте собственный Fork по [инструкции](docs/SUBMISSION.md).

## Проверки

```sh
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode smoke
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode base
docker compose --profile test run --build --rm tests python tests/run_tests.py --mode expert
```

smoke проверяет каркас и проходит до исправлений. base включает smoke и 10 обязательных сценариев на **60 баллов**. expert включает оба набора и два дополнительных сценария без добавочных баллов. Падение теста даёт ненулевой код выхода. Результаты сохраняются в reports/&lt;mode&gt;-results.json и .md. Тесты используют реальные PostgreSQL/Redis, отдельную SQL-схему и случайные префиксы ключей. Демонстрационные данные приложения они не удаляют. Подробнее: [сценарии](docs/TEST_CASES.md).

Готовность: все обязательные сценарии проходят, в БД остаётся одна бронь при гонке, неверные и истёкшие токены отклоняются, перезапуск API сохраняет данные. Нужны также заполненный отчёт и доступное видео. Оценка: 60 за функциональность, 25 за видео, 10 за отчёт, 5 за качество кода. Уровень Э требует обоих дополнений; [точная шкала](docs/GRADING.md).

Стенд предназначен для локального обучения. clientId служит меткой, доказательство владения даёт секретный holdId. Пользовательская аутентификация, платежи, высокая доступность Redis и общая транзакция Redis/PostgreSQL в объём работы не входят. Во время редкой гонки можно выдать удержание уже забронированного ресурса; повторную подтверждённую бронь должна запрещать БД.
